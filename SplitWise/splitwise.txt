Requirements:

Functional Requirements

1.  Users can create an account with name and email.
2.  Users can create a group.
3.  Users can add members to or remove members from a group.
4.  Users can add an expense to a group by specifying: 4.1. Expense
    creator 4.2. User who paid the expense 4.3. Description and total
    amount 4.4. Participants and their split details
5.  Expenses can be split using the following strategies: 5.1. Equally
    among participants 5.2. Exact amount for each participant 5.3.
    Percentage-wise 5.4. Share-wise (for example, 2:1:1)
6.  Users can edit an existing active expense.
7.  Users can delete an existing active expense.
8.  The system maintains a ledger of expense, reversal, and settlement
    entries.
9.  Users can view their net balance in a group: 9.1. Positive balance
    means the user should receive money. 9.2. Negative balance means the
    user owes money.
10. Users can view simplified “who owes whom” balances.
11. Users can manually settle an outstanding amount with another group
    member.
12. Settlement must not exceed the amount owed by the payer or the
    amount receivable by the receiver.
13. A removed member’s existing financial obligations remain available
    for settlement.
14. The same users can participate in multiple groups, and each group’s
    balances are maintained independently.

Non-Functional Requirements

1.  Financial consistency: split amounts must add up exactly to the
    expense total.
2.  Validation: invalid users, groups, participants, split values, and
    settlement requests must be rejected.
3.  Monetary precision: amounts are represented as integer paise rather
    than floating-point values.
4.  Auditability: expense edits and deletions are reflected through
    reversal ledger entries instead of deleting historical ledger
    records.
5.  Deterministic balance simplification: simplified debts are generated
    in a deterministic order.
6.  Concurrency: the design should protect concurrent expense and
    settlement operations from inconsistent balance updates. (The
    current in-memory implementation does not implement
    synchronization.)

Out of Scope / Not Implemented in the Current Code

1.  Actual online payment processing or integration with a payment
    gateway.
2.  Notifications to group members when an expense is added, edited, or
    deleted.
3.  Persistent database storage.
4.  Authentication and authorization.
5.  Explicit concurrency control such as mutexes or database
    transactions.
6.  Automatic reminders for pending settlements.

Core Entities and Relationships

1.  User
    -   Represents a registered user.
    -   A user can belong to multiple groups.
2.  Group
    -   Represents an expense-sharing group.
    -   A group contains multiple GroupMember records.
3.  GroupMember
    -   Represents a user’s membership and status in a group.
    -   Membership status can be ACTIVE or REMOVED.
    -   Removing a member does not erase their existing financial
        obligations.
4.  SplitInput
    -   Contains the input required to calculate a participant’s share.
    -   Depending on the split strategy, it carries exact amount,
        percentage, or shares.
5.  ExpenseSplit
    -   Stores the final calculated amount assigned to a participant.
6.  SplitStrategy
    -   Abstract strategy used to calculate expense shares.
    -   Implementations: 6.1. EqualSplitStrategy 6.2. ExactSplitStrategy
        6.3. PercentageSplitStrategy 6.4. SharesSplitStrategy
7.  Expense
    -   Represents an expense created in a group.
    -   Stores creator, payer, amount, description, split type, and
        calculated splits.
    -   Expense status can be ACTIVE or DELETED.
8.  LedgerEntry
    -   Represents a financial change for a user in a group.
    -   Ledger entry types: 8.1. EXPENSE 8.2. REVERSAL 8.3. SETTLEMENT
9.  Settlement
    -   Represents a manual settlement between two users in a group.
10. SplitwiseManager
    -   Main class that coordinates users, groups, expenses, split
        strategies, ledger operations, balance calculations, and
        settlements.

Relationships

1.  A User can belong to many Groups.
2.  A Group contains multiple GroupMember records.
3.  A GroupMember refers to one User through userId.
4.  A Group can contain many Expenses.
5.  An Expense has one creator and one payer.
6.  An Expense contains multiple ExpenseSplit records.
7.  SplitwiseManager owns and coordinates the users, groups, expenses,
    ledger entries, settlements, and split strategies.
8.  An Expense can produce multiple LedgerEntry records.
9.  Editing or deleting an Expense adds reversal entries to the ledger.
10. A Settlement produces ledger entries for both the payer and
    receiver.

Important Notes About the Current Implementation

1.  Money is stored as long long in paise.
2.  Percentage values use basis points: 5000 represents 50%, and the
    total percentage must be 10000.
3.  The equal, percentage, and shares strategies assign any rounding
    remainder to the last participant so the split total remains exact.
4.  The ledger stores the payer’s credit and each participant’s debit.
5.  Positive net balance means the user should receive money; negative
    means the user owes money.
6.  Simplified balances are calculated by matching debtors with
    creditors.
7.  Settlement updates both users’ balances through ledger entries.
8.  The code includes no Notification class, Payment class, or
    notification delivery/payment gateway flow. A settlement is a
    recorded manual settlement, not an actual online payment
    transaction.
9.  Although concurrency is a requirement in the proposed system, the
    current code is an in-memory implementation without locks or
    transactional synchronization.
