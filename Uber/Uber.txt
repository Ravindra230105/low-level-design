Uber (Ride Booking System)


Final Requirements

1. Rider can book a ride by providing pickup and destination locations.
2. Rider can choose a vehicle type such as CAR, BIKE or AUTO.
3. System finds an available driver matching the requested vehicle type.
4. Driver can accept a ride request.
5. Rider can cancel a ride before it starts.
6. Driver can cancel a ride before it starts.
7. Driver can start an accepted ride.
8. Driver can complete a ride.
9. Fare is calculated using a fare strategy.
10. Rider can rate the driver after a ride is completed.
11. Driver location can be updated.
12. Concurrent ride requests must not assign the same driver to multiple rides.

Flow :

Rider
-> Enter Pickup and Destination
-> Select Vehicle Type
-> Request Ride
-> RideManager finds nearest available Driver
-> Driver receives notification
-> Driver accepts Ride
-> Ride starts
-> Driver completes Ride
-> Fare calculated
-> Rider rates Driver


Driver :

Driver
-> Receives Ride Request
-> Accept Ride
-> Start Ride
-> Complete Ride

Driver can also cancel a ride before it starts.

Design Patterns Used

1. Strategy Pattern
   - DistanceStrategy
   - DriverFindStrategy
   - FareStrategy

2. Observer Pattern
   - Ride extends Subject.
   - Rider and Driver implement Observer.
   - Ride notifies both of them on request, accept, start, complete and cancel.

3. Singleton Pattern
   - RideManager is a single shared manager for ride assignment.

4. Builder Pattern
   - Ride::Builder creates Ride objects.

5. Decorator Pattern
   - SurgeFare, RiderPassDiscount and CouponDiscount wrap any FareStrategy,
     so pricing rules can be stacked without touching the base strategies.

6. Factory Pattern
   - UserFactory creates Rider and Driver objects.

State handling
   - The ride states have no behaviour of their own, only allowed transitions,
     so a class per state is not needed.
   - Ride keeps a RideStatus and a small transition table in canMoveTo().
     REQUESTED  -> ACCEPTED, CANCELLED
     ACCEPTED   -> IN_PROGRESS, CANCELLED
     IN_PROGRESS-> COMPLETED
     COMPLETED / CANCELLED are terminal.


Concurrency

1. Multiple riders can request rides at the same time.
2. RideManager protects driver assignment using a mutex.
3. Driver availability is checked and changed while holding the same mutex.
4. Therefore two concurrent requests cannot reserve the same available driver.
5. Ride state changes are also protected by RideManager's mutex.


Important Design Decision

The domain relationship is:

Rider -> Ride -> Driver
             |
             -> Vehicle
             -> Pickup
             -> Drop

RideManager owns the ride-booking workflow.

Driver matching is kept separate using DriverFindStrategy so another strategy can be added later, such as:
- nearest driver
- highest rated driver
- lowest ETA driver

Distance calculation is kept separate using DistanceStrategy so the application can switch from simple Euclidean distance to Manhattan distance or a real map/routing implementation.

Fare calculation is also kept separate using FareStrategy so different pricing models can be added without changing Ride. FareStrategy only receives the distance, not the whole Ride, so pricing has no dependency on the ride object. Surge and discounts are applied with the Decorator pattern on top of a base strategy, for example :

    FareStrategy* fare =
        new CouponDiscount(
            new SurgeFare(new BaseFareStrategy(), 1.5),
            30
        );

RideManager wraps the strategy with RiderPassDiscount automatically when the rider has a rider pass.

All ride actions go through RideManager, which owns the mutex, so no entity calls back into the manager and every state change stays inside one lock.
